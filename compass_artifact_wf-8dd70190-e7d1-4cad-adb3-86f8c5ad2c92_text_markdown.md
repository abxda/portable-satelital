# Running a `pyshepseg` Geospatial ML Notebook Entirely in WebAssembly: An Expert's 2025–2026 Roadmap

## TL;DR
- **It is genuinely achievable for an expert** — but the single hard blocker is `numba`, which cannot JIT inside WASM because llvmlite/LLVM runtime codegen is incompatible with the WASM sandbox; everything else (GDAL, GEOS, PROJ, shapely, geopandas, rasterio, scikit-learn, scikit-image) is already shipped in Pyodide 0.29.4, so the geospatial stack is mostly a solved problem.
- **The recommended architecture is a hybrid:** keep the Pyodide/JupyterLite notebook, reimplement the two `pyshepseg` numba hot loops (clumping + iterative small-segment elimination) as a Rust/C core compiled to a WASM side module loaded by Pyodide, replace `exactextract` with pure-numpy/`scipy.ndimage` zonal stats (segments are pixel-aligned, so exact partial-pixel coverage is unnecessary), and stream the 2.66 GB image as a Cloud-Optimized GeoTIFF tile-by-tile rather than loading it whole.
- **Realistic effort for one expert developer:** roughly 3–6 months for a robust, fully in-browser pipeline that preserves the actual Shepherd algorithm; the Rust WASM segmentation core and the data-streaming architecture are the long poles, not the scikit-learn/pandas parts.

## Key Findings

**Blocker A — numba in WASM (the hard one): genuinely impractical to run unchanged; solvable only by reimplementation.** numba depends on `llvmlite`, which embeds an LLVM JIT that emits native machine code at runtime — fundamentally incompatible with WASM's sandbox, which forbids runtime native codegen. The Pyodide maintainers reached this conclusion early: in Pyodide GitHub issue #621 (opened by "rth" on March 10, 2020, and still open), the assessment was "I'm somewhat dubious this would work without major effort, as essentially it's not that far from building parts llvm with llvm for Webassembly." numba is NOT in the Pyodide package list and never has been. numba's own AOT path (`numba.pycc`) is deprecated and being removed (pending-deprecation since 0.57; the docs note it was deprecated "in favour of developing new technology"), and even when present it produced Python-only C-extensions incompatible with WASM. **There is no path to running numba-jitted code as-is in Pyodide.** The only viable routes are (i) pure-numpy/scipy reimplementation of the `pyshepseg` kernels, or (ii) rewriting the hot loops in Rust/C and compiling to a WASM module.

**Blocker B — GDAL/GEOS/PROJ in WASM: already solved.** Contrary to common assumption, the entire native geostack is shipped in current Pyodide. Verified versions in Pyodide 0.29.4: shapely 2.1.2, pyproj 3.7.2, geopandas 1.1.3, fiona 1.9.5, rasterio 1.5.0, plus gdal/geos/libproj as bundled C libraries, affine 2.4.0, and cartopy 0.25.0. So `rasterio.features.shapes`, `rasterio.features.rasterize`, geopandas reprojection (pyproj/PROJ), and shapely/GEOS union/difference all work in the browser today. (Caveat: the raw `from osgeo import gdal` bindings have a known import-reliability bug, but rasterio/fiona/geopandas — which wrap GDAL internally — are the supported entry points.) Outside Python, `gdal3.js` (an Emscripten port of `gdal_translate`, `ogr2ogr`, `gdal_rasterize`, `gdalwarp`, `gdaltransform`, bundling GDAL, PROJ, GEOS, SQLite, GeoTIFF, etc.) and `geotiff.js` provide JS/WASM GDAL and COG reading.

**Blocker C — exactextract in WASM: not ported, but unnecessary here.** exactextract is a C++/pybind11 library hard-depending on GEOS+GDAL; verification of its issue tracker found it has never been compiled to WASM and there is no issue/PR proposing it. Crucially, exactextract's value is *exact partial-pixel coverage* for vector polygons over a raster ("it takes into account raster cells that are partially covered by the polygon"). In this pipeline the "zones" are the segment-ID raster itself — pixel-aligned with the 12-band image. Therefore exact coverage fractions are irrelevant: every pixel belongs wholly to exactly one segment. The zonal spectral statistics (min/max/mean/stdev/sum per band per segment) reduce to grouped reductions over a label array, which `numpy` and `scipy.ndimage` compute directly (the `scipy.ndimage` zonal-stats pattern is well established) and which run unmodified in Pyodide. This eliminates the C++ dependency entirely and likely runs faster than the original 13-minute exactextract pass.

**Blocker D — 2.66 GB in the browser: must stream, do not load whole.** WASM is 32-bit (wasm32) by default with a hard ~4 GB linear-memory ceiling; a single 2.66 GB array plus working copies will not fit. Memory64 (wasm64) shipped in Chrome 133 and Firefox 134 in early 2025 (per Mozilla's "Intent to ship" for Firefox 134, bug 1929590, and Chrome Platform Status for Blink 133; caniuse confirms "Not supported" through Chrome 132/FF 133 and "Supported" from Chrome 133/FF 134) and is part of the finalized WebAssembly 3.0 standard (published Sept 17, 2025 by Andreas Rossberg at webassembly.org, which expands "the available address space... from 4 gigabytes to (theoretically) 16 exabytes"). However, browser engines cap it at 16 GB (the limit set in the memory64 spec js-api §1785; Mozilla's intent-to-ship notes memories "currently up to 8GiB, soon up to 16GiB"), it is not yet in Safari, and it imposes a meaningful slowdown because bounds checks can no longer be elided — per Mozilla's SpiderMonkey blog (Jan 15, 2025), the penalty "can range from just 10% to over 100%—a 2x slowdown just from changing your pointer size," since 32-bit wasm reserves 4 GB so "we can omit all bounds checks entirely... This optimization is impossible for Memory64." The correct architecture is to convert the source to a Cloud-Optimized GeoTIFF (COG) and process it tile-by-tile via HTTP range requests — exactly the model `pyshepseg.tiling.doTiledShepherdSegmentation` already uses (per the pyshepseg docs it "Runs the segmentation on separate (overlapping) tiles across the raster, then stitches these together... The initial spectral clustering is performed on a sub-sample of the whole raster (using fitSpectralClustersWholeFile), to create consistent clusters"), and exactly what `geotiff.js` does in-browser via `readRasters({window})`. Persist intermediate rasters in the Origin Private File System (OPFS), which Pyodide can mount as a native filesystem via `mountNativeFS`.

**Blockers E/F — architecture and building blocks.** A full Pyodide+JupyterLite static site is feasible; the only custom artifact required is the WASM segmentation core. The richest precedents for the heavy/visualization pieces are: scikit-image 0.25.2 (`skimage.segmentation.slic`, `felzenszwalb` — pure-C/Cython, numba-free) as a segmentation reference; Rust crates `geo`, `ndarray`, `geozero` (zero-copy geospatial I/O), and `linfa` (which explicitly supports a `wasm-bindgen` feature for browser-style WASM on `wasm32-unknown-unknown`, and whose linfa-ensemble 0.8.1 exposes `RandomForestParams` — e.g. `RandomForestParams::new(DecisionTree::params()).ensemble_size(100)` — plus "A fitted AdaBoost ensemble classifier"); `sklearn-onnx` + ONNX Runtime Web for client-side inference; and lonboard/deck.gl-geoarrow for GPU-rendering the segment polygons (deck.gl-geoarrow has demonstrated 3.2 million points and multi-threaded polygon triangulation off the main thread).

## Details

### The exact pipeline, step by step, in WASM

| Step | Original dependency | WASM status | Action |
|---|---|---|---|
| 1. Read 12-band GeoTIFF (2.66 GB) | rasterio (GDAL) | rasterio 1.5.0 in Pyodide; geotiff.js for COG | Convert to COG; stream tiles via range requests / OPFS |
| 2. Shepherd segmentation | pyshepseg (numba + sklearn KMeans) | **numba blocked**; KMeans OK (sklearn 1.8.0) | Reimplement clumping + elimination in Rust/WASM; keep KMeans seeding in sklearn |
| 3. Polygonize + dissolve + GeoPackage | rasterio.features.shapes, geopandas (GDAL/GEOS) | All in Pyodide | Works as-is |
| 4. Label raster (locality polygons, reproject, union/diff, rasterize) | geopandas, pyproj, shapely, rasterio.features.rasterize | All in Pyodide | Works as-is |
| 5. Zonal class proportions (np.bincount) | numpy | numpy 2.4.3 in Pyodide | Works as-is |
| 6. Zonal spectral stats (12 bands) | exactextract (C++ GEOS/GDAL) | **not ported** | Replace with numpy/scipy.ndimage grouped reductions over segment-ID raster |
| 7. Features table → CSV | pandas | pandas in Pyodide | Works as-is |
| 8. Classification (StandardScaler + StackingEstimator[MLP, ExtraTrees]) | scikit-learn | sklearn 1.8.0 in Pyodide | Works as-is; or export to ONNX for JS inference |
| 9. Predict, join, render map, export GeoPackage | sklearn, geopandas, matplotlib | All in Pyodide | Works; optionally lonboard/deck.gl for large polygon rendering |

### The Shepherd segmentation core (the crux)

The algorithm — Shepherd, J.D.; Bunting, P.; Dymond, J.R. "Operational Large-Scale Segmentation of Imagery Based on Iterative Elimination." *Remote Sensing* 2019, 11(6), 658, doi:10.3390/rs11060658 (the RSGISLib/pyshepseg basis) — has three phases: (1) K-means clustering to seed segments (sub-sampled), (2) "clumping" — assigning each pixel to its cluster and labelling connected components, and (3) iterative elimination of clumps below the minimum-segment-size threshold by merging each into the spectrally-closest (Euclidean in colour) neighbour, then relabelling to contiguous IDs. Phases 2 and 3 are exactly the parts pyshepseg accelerates with numba's `@njit` (including a jit-dictionary `RowColArray` structure mapping segments to their pixels), because they are tight, branch-heavy, pointer-chasing loops that are catastrophically slow in pure Python.

Two reimplementation options:

1. **Pure numpy/scipy in Pyodide (fastest to build, slowest to run).** Connected-component labelling maps to `scipy.ndimage.label`; per-segment statistics map to `scipy.ndimage` grouped functions. The K-means seeding stays in scikit-learn. The genuine difficulty is the *iterative small-segment elimination*: it is inherently sequential (each merge changes the neighbour graph), so it does not vectorize cleanly. A pure-Python/numpy version will work but can be one to two orders of magnitude slower than the numba original on a full-resolution tile — acceptable for a single AOI tile, painful for the whole 10005×11086 scene.

2. **Rust (or C/C++) compiled to a WASM module, called from Pyodide (recommended).** This is the "genius developer" leverage point. Rewrite only the clumping and elimination kernels in Rust using `ndarray`, expose a clean `segment(tile: &[f32], width, height, min_size, ...) -> Vec<u32>` API, compile with `wasm-bindgen` (or as an Emscripten side module). Pyodide can load custom compiled wheels/side modules (`micropip.install(url)` for Emscripten wheels; the `lincoln-lm/numba-wasm-example` project demonstrates the side-module pattern, and Pyodide ships an Emscripten toolchain via `pyodide build`). This recovers near-native speed while preserving the *exact* algorithm. The Rust geospatial ecosystem (`geo`, `geozero`, `image-tiff`, `fast-slic-rust`, `simple_clustering`) provides building blocks and reference connected-component/superpixel code, though none implements Shepherd specifically — the elimination loop must be hand-ported.

A pre-existing Emscripten ABI subtlety to plan for: Pyodide pins specific Emscripten versions per release (e.g. the 0.27+ line moved to Python 3.13 / Emscripten 4.0.9), and WASM wheels must match the exact `pyodide_2024_0_wasm32`-style platform tag, so the Rust/C module must be built against the matching toolchain.

### The classification step and ONNX option

The scikit-learn pipeline runs natively in Pyodide (sklearn 1.8.0). If you prefer to drop Python for inference, `sklearn-onnx` converts StandardScaler, MLPClassifier, and ExtraTreesClassifier — all three are in skl2onnx's supported-operators list — and the model runs via ONNX Runtime Web (WASM CPU backend, where "All ONNX operators are supported by WASM," or the WebGPU backend). The one wrinkle: a *custom* `StackingEstimator` wrapper is not a standard sklearn class, so skl2onnx will not convert it out of the box; you must either register a custom converter (via `update_registered_converter`) or refactor the stack into sklearn's native `StackingClassifier` (which *is* in skl2onnx's supported list). Training in the browser is fine in Pyodide; for ONNX you would train offline and ship the `.onnx`.

### Large-data architecture

- Convert the 2.66 GB source once (offline or server) to a tiled, overviewed COG (`gdal_translate ... -co TILED=YES -co COPY_SRC_OVERVIEWS=YES -co COMPRESS=LZW`; recommended internal block size 256×256 or 512×512).
- In-browser, read only the AOI/tile windows via `geotiff.js` `readRasters({window})` or rasterio's windowed reads over a vsicurl-style range source.
- Mirror `pyshepseg`'s tiling: segment overlapping tiles, stitch across boundaries. The initial K-means is fit on a uniform sub-sample of the whole image for consistent cluster seeds across tiles.
- Store intermediate segment-ID and label rasters in OPFS (Pyodide `mountNativeFS`).
- Reserve Memory64 only as a fallback if a single tile genuinely needs >4 GB; expect a 10%–2× performance penalty and no Safari support.

### Architecture options compared

1. **Pure Pyodide notebook in JupyterLite (static site, e.g. GitHub Pages).** Everything except numba already works. Effort dominated by the segmentation core. If you take the pure-numpy elimination route, this is the least code but risks unacceptable runtime on the full scene. **Effort: ~5–8 person-weeks** (mostly Milestones 0–2). Best for: faithful notebook reproduction, AOI-sized tiles.
2. **Hybrid: Rust/WASM segmentation + zonal-stats core, Pyodide for the rest (RECOMMENDED).** Custom Rust side module for the two hot loops; numpy/scipy for zonal stats; Pyodide sklearn/pandas/geopandas for everything else. **Effort: ~3–6 person-months.** Best speed-to-effort ratio; preserves the exact algorithm. Main risk: Emscripten ABI/toolchain matching and the hand-port of the elimination loop.
3. **Pure JS/TS + WASM (drop Python).** Segmentation + zonal stats as Rust/WASM, geospatial via gdal3.js/geotiff.js/turf.js, ML via ONNX Runtime Web, rendering via deck.gl-geoarrow/lonboard. **Effort: ~6–9 person-months.** Best raw performance and smallest runtime, but the largest rewrite and you lose the notebook. Best for: a production web app, not a reproducible notebook.
4. **Pre-compute heavy steps server-side, ship only inference + interactive map.** Segmentation + features computed once server-side; browser does only ONNX inference and rendering. **Effort: ~3–5 person-weeks.** Lowest browser effort and risk, but violates the "entirely in-browser" goal for the heavy steps. Best as a pragmatic fallback or first milestone.

## Recommendations

**Pursue Option 2 (hybrid Pyodide + Rust/WASM core).** Concrete staged plan:

1. **Milestone 0 — De-risk (1–2 weeks).** Stand up JupyterLite with Pyodide 0.29.4; confirm rasterio 1.5.0, geopandas 1.1.3, shapely 2.1.2, pyproj 3.7.2, scikit-learn 1.8.0 all import and run steps 3–9 on a small pre-segmented tile. This validates that the entire pipeline *except* segmentation already works in-browser.
2. **Milestone 1 — Zonal stats without exactextract (1 week).** Replace step 6 with numpy/`scipy.ndimage` grouped reductions over the segment-ID raster. Validate min/max/mean/stdev/sum per band against the original exactextract output on a reference tile (should match to floating-point tolerance because segments are pixel-aligned).
3. **Milestone 2 — Pure-numpy Shepherd (2–4 weeks).** Reimplement clumping (`scipy.ndimage.label`) and iterative elimination in pure Python/numpy; validate segment-for-segment against pyshepseg on a small tile. Accept slow runtime — this is the correctness oracle.
4. **Milestone 3 — Rust/WASM segmentation core (4–8 weeks).** Port the clumping + elimination kernels to Rust (`ndarray`), build against Pyodide's pinned Emscripten toolchain, load as a side module / Emscripten wheel via micropip. Benchmark against Milestone 2 for correctness and against native pyshepseg for speed.
5. **Milestone 4 — Streaming + tiling (3–5 weeks).** COG conversion, `geotiff.js`/windowed reads, OPFS intermediate storage, tile stitching mirroring `pyshepseg.tiling`. This is what makes the 2.66 GB scene tractable.
6. **Milestone 5 — Rendering + polish (1–2 weeks).** matplotlib for the static map; optionally lonboard/deck.gl-geoarrow for interactive rendering of the classified polygons.

**Thresholds that change the plan:**
- If the target is only an AOI-sized tile (not the full scene), stop after Milestone 3 with the pure-numpy core — the Rust module may be unnecessary.
- If full-scene interactive performance is required, the Rust/WASM core (Milestone 3) becomes mandatory, not optional.
- If you cannot preserve a true in-browser heavy compute (timeline/risk), fall back to Option 4 (server-side pre-compute) as a shippable interim.
- If Safari support is mandatory, do not rely on Memory64 or WebGPU; design for wasm32 + tiling and the ONNX WASM CPU backend.

## Caveats
- "rasterio is not available in Pyodide" is a common but outdated belief; the verified current fact is rasterio 1.5.0 is shipped in Pyodide 0.29.4. However, the raw `osgeo.gdal` Python bindings have a documented import bug, so route GDAL access through rasterio/fiona/geopandas.
- The numba blocker is real and not going away: there is no production numba-on-WASM. The `lincoln-lm/numba-wasm-example` project is an experimental proof-of-concept that compiles specific annotated functions' LLVM IR to WASM side modules ahead of time — it is not a drop-in for arbitrary `@njit` code and should be treated as inspiration, not a dependency.
- Performance numbers for the pure-numpy elimination loop are estimates, not benchmarks; the sequential merge step is the chief uncertainty and should be measured early (Milestone 2). The 13-minute exactextract figure is from the user's local full-image run, not a browser measurement.
- Memory64/WASM 3.0 figures (16 GB engine cap, Chrome 133/Firefox 134, no Safari, finalized Sept 17, 2025) are accurate as of the report date but the browser landscape moves quickly; re-verify Safari status before committing.
- Exactly reproducing pyshepseg's output requires matching its tie-breaking and merge-order behaviour; expect small boundary differences between any reimplementation and the numba original, which must be validated tile-by-tile.
